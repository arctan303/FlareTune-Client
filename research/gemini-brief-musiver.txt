1. 先说结论
=====================================================================

顶部那条东西不是装饰，它同时是两样东西：

  A. 一个"按钮"——测试标签 player.collapseButton，
     38dp × 38dp 热区、主题色、ripple、可点击，点它收起全屏播放页。

  B. 一个"整页拖动"的视觉把手——播放页根节点套了一层垂直方向的
     draggable，拖动的结果由一个 Animatable<Float> 的纵向位移量承载，
     松手时按"位置比例 + 速度"两重条件决定"回弹还是关掉"。

  关键数字（都能在字节码里读到）：
     位置阈值   0.3 / 0.7（占总高度的比例，构成滞回带）
     速度阈值   +1800 / -1600（甩动逃逸，单位 px/s 量级）
     落定动画   spring(dampingRatio = 0.8, stiffness = 308)
     "已完全展开"判定   位移 <= 0.5

2. 这个页面长什么样（结构层）
=====================================================================

单 Activity，全部在 Compose 内部换页：
  cn.musiver.android.ui.MainActivity
  launchMode = singleTop
  configChanges 覆盖了方向 / 屏幕尺寸 / 字体缩放等一大串，
  也就是说转屏、折叠屏展开都不会重建 Activity，全在 Compose 里重排。
  整个 APK 只有这一个 Activity（其余是支付宝 / 计费 / Glance 小组件的
  第三方 Activity）。 [DEX]

播放页代码归属：cn.musiver.android.ui.player
  · PlayerViewModel            播放页的 ViewModel
  · ImmersiveChromeState       沉浸式 chrome 的状态
  · LyricSearchEvent           歌词搜索事件

播放页的根容器打了测试标签 player.nowPlayingScreen，
内部再分成"推荐 / 歌曲 / 歌词"几个 tab（选中态存在
NowPlayingLayoutState.selectedPlayerTab 里，歌词 tab 的标签是
player.lyricsTab）。 [DEX]

横屏是另一套布局：出现 player.landscapeDismissButton、
player.landscapeMetadataLine、player.landscapePlayPauseButton、
player.landscapeNextButton、player.landscapeSkipForwardButton、
player.landscapeFavoriteButton。 [DEX]
（真机实测那台折叠屏当时就是横屏，1070×668dp。）


=====================================================================
3. 顶部那条：collapseButton 的构造
=====================================================================

反编译到的组合函数只接收一个 Modifier，函数体里挂上
player.collapseButton 标签。从 smali 能逐条读出来： [DEX]

  · 尺寸：DpSize(38f, 38f) → Modifier.size(38.dp, 38.dp)
    两个参数都是 0x42180000 = 38.0f。
    38dp 是"点击热区"，不是那条横条本身的视觉尺寸。

  · 不透明度：Modifier.alpha(1.0f)（常量 0x3F800000）。

  · 颜色：一组 4 个 Color 的容器（IconButtonColors 那种形状）：
        a = containerColor
        b = contentColor
        c = disabledContainerColor
        d = disabledContentColor
    enabled 时背景取 a、内容取 b；disabled 时取 c / d。
    这 4 个颜色从当前 MaterialTheme 的 colorScheme 现算，
    其中一份派生色带 alpha = 0.7f（常量 0x3F333333）。

  · 交互反馈：InteractionSource + indication（ripple），
    点下去有水波纹。

  · 点击回调：NowPlayingPlaybackCallbacks.onCollapseClick。

  · 内容：外层传入的可组合 lambda（横条本体在里面画）。


=====================================================================
4. 拖动：从手势到"关掉/回弹"的完整链路
=====================================================================

4.1 手势挂在哪
---------------------------------------------------------------------
播放页根节点（带 player.nowPlayingScreen 的那一层）外面套了一个
垂直方向的拖动容器。 [DEX]

  a) 对根 Modifier 追加了一个 draggable 型修饰符，参数顺序是
     (state, orientation, enabled, interactionSource,
      startDragImmediately, onDragStarted, onDragStopped, reverseDirection)。
  b) 方向常量取自 Orientation 枚举的 a 号常量。
     该枚举 <clinit> 里两个字面量是 "Vertical"(索引 0)、"Horizontal"(索引 1)，
     所以 a = Vertical。
     ——R8 把枚举声明顺序调过，不能按 Compose 源码顺序猜，必须看 <clinit>。
  c) 拖动状态是"把增量累加进一个 float 状态"的实现：
     先 remember 一个 float 可变状态（初值由调用方给），
     再包一层 DraggableState，dispatchRawDelta(F) 时把 delta 加进去。
  d) 挂了一个 onDragStarted 的 suspend 回调。

4.2 拖动是页面级契约，不是局部补丁
---------------------------------------------------------------------
页面状态 bundle 里直接有这两个字段： [DEX]

    NowPlayingUiCallbacks(
        onPlayerTabSelected = ...,
        onVerticalDrag      = ...,   // 可空 lambda，参数 Float
        onDragEnd           = ...,   // 可空 lambda，无参
        onDlnaCastClick     = ...,
        isDlnaActive        = ...    // Boolean
    )

两个 lambda 都可空，说明设计上允许"这个布局不接管拖动"
（电视端 / 横屏之类）。
它们在路由级 composable 里创建，一路传到页面状态里。

4.3 位移量与初值
---------------------------------------------------------------------
路由级组合函数里有一个 Animatable<Float>： [DEX]

  · 初值 = 从窗口信息里取一个整型尺寸（打包 long 的低 32 位）
    再转成 float，也就是"容器高度"。
    → 页面初始位移 = 满高度，即从屏幕下方进来。
  · 另有一个 Float 状态用 Float.NaN 作初值（0x7FC00000），
    用来表示"还没被赋值"。
  · "是否已经完全展开"的判定是：位移 <= 0.5f
    （常量 0x3F000000，半像素级容差，等价于"位移基本为 0"）。

4.4 松手判定：位置比例 + 速度，双条件
---------------------------------------------------------------------
判定逻辑在拖动协程里，输入四个量（全部读自字节码）： [DEX]

    pos    = 当前位移（从一个 MutableState<Float> 读出来）
    height = 页面高度（就是被 0.3 / 0.7 乘的那个基数）
    speed  = 本次事件携带的速度
    flag   = 一个捕获进来的布尔（拖动开始时的状态快照）

处理顺序是固定的：

    if (height <= 0f) → 跳过全部判定，直接进落定动画      // 防御性守卫
    pos = pos.coerceIn(0f, height)                        // 夹在 [0, height]

    然后是两个对称的比较块：

      块一：cmpl(pos, 0.3f * height)     // 0.3f  = 0x3E99999A
            位置没过 0.3h 时，再比 cmpl(speed, +1800f)   // 0x44E10000

      块二：cmpg(pos, 0.7f * height)     // 0.7f  = 0x3F333333
            位置在 0.7h 以内时，再比 cmpg(speed, -1600f) // 0xC4C80000

    结果写进一个布尔，然后：
      Boolean.valueOf(结果) 经 Lqn2;->invoke 回调出去（交给外层）

  · 0.3 与 0.7 是两个不同的数，不是同一个阈值写了两遍 ——
    这是一条**滞回带**：中间 30%~70% 区间维持原状态，不翻转。
  · 速度阈值是**不对称**的：一侧 1800、另一侧 -1600，
    符号相反、绝对值不等，说明两个方向的甩动判据本来就不一样。
  · 两个块共用同一个尾部（R8 把两块交叉合并了：块一在
    "位置没过、速度也不够"时会**贯穿**掉进块二的入口，
    块二开头那句 if-nez 就是为这个贯穿路径设的守卫）。
    所以"哪一块对应收起、哪一块对应展开"没法从控制流直接读出来，
    见第 11 节。

  真正确定的是这个布尔**决定什么**：
      if (布尔 == true)  目标值 = 0f        // 回到原位
      else               目标值 = height    // 移到满高度（移出屏幕）
    然后目标值交给第 4.5 节的 spring 动画。

4.5 落定动画
---------------------------------------------------------------------
判定完之后统一走同一套落定动画： [DEX]

    spring(dampingRatio = 0.8f,   // 0x3F4CCCCD
           stiffness    = 308f,   // 0x439A0000
           visibilityThreshold = null)

  · dampingRatio 0.8 = 偏"稳"，只带一点点回弹
    （Compose 内置档位里 1.0 是无弹、0.75 是低弹、0.5 是中弹）。
  · stiffness 308 介于 StiffnessLow(200) 与 StiffnessMediumLow(400) 之间，
    手感偏"慢而稳"，不是那种很脆的快弹。
  · 目标值只有两个：0f（回弹）或 height（收起）。
  · 动画是对 Animatable<Float> 调的 animateTo，带一个 12（0xC）
    的 flag 参数（Compose 里 animateTo 的默认参位）。

  还有一条分支：某些布局模式下（枚举常量 Lv45.b，看名字像是
  横屏/大屏那类布局）用的是 snapTo 而不是 animateTo，
  即不做过渡、直接到位。 [DEX]

4.6 一条完整的手势时间线（据此还原）
---------------------------------------------------------------------
   手指按下       → draggable 起手，onDragStarted
   手指移动       → 位移量跟着增量累加（页面整体下移）
   手指抬起       → 算速度，按 4.4 的双条件决定"收起 / 回弹"
                    → 回调把结果布尔抛给外层
                    → Animatable 用 spring(0.8, 308) 动到目标值
   真的收起       → 外层把这一层收掉（见第 6 节：不经过 ViewModel）
   点一下把手     → 走 onCollapseClick，同样的收起动效

5. 页面状态是怎么分组的（这套代码最值得注意的结构）
=====================================================================

播放页不用"一个巨型 State"，而是拆成 5 个回调 bundle + 2 个纯数据，
每个都是 Kotlin data class，字段名能从 toString 字面量完整读出来： [DEX]

  NowPlayingUiCallbacks(
      onPlayerTabSelected,
      onVerticalDrag,
      onDragEnd,
      onDlnaCastClick,
      isDlnaActive)

  NowPlayingPlaybackCallbacks(
      onCollapseClick,            // ← 顶部那条的点击
      onPlayPauseClick,
      onPreviousClick,
      onNextClick,
      onSkipBackwardClick,
      onSkipForwardClick,
      onSeekTo,
      onPlaybackModeClick,
      onLoopPlaybackClick,
      onQueueClick,
      onVolumeChange, ...)

  NowPlayingTrackCallbacks(
      onToggleFavorite,
      onMoreClick,
      onTrackTitleClick,
      onArtistClick,
      onAlbumClick)

  NowPlayingLyricsCallbacks(
      onRetryLyrics,
      onSeekToLyricLine,
      onLyricsDragStateChange,
      onLyricsDragFinished)

  NowPlayingSleepTimerCallbacks(
      onSetSleepTimer,
      onSleepTimerStopAfterCurrentTrackChanged,
      onCancelSleepTimer)

  NowPlayingLayoutState(selectedPlayerTab=...)      // 纯数据：当前 tab
  NowPlayingGradientColors(top=..., bottom=...)     // 纯数据：背景渐变色

分组维度是"交互域"（框架级 / 播放控制 / 曲目信息 / 歌词 / 睡眠定时），
不是"按组件"。这样任何子组件只拿它需要的那一组，
不用把整页的回调表一路往下传。

6. 收起这个动作不经过 ViewModel
=====================================================================

播放页里出现的、指向 PlayerViewModel 的 Kotlin 方法引用一共 12 个，
字符串常量原样抄下来是： [DEX]

    togglePlayPause()V
    skipForwardBySeconds()V
    skipBackwardBySeconds()V
    cyclePlaybackMode()V
    cancelSleepTimer()V
    dismissDlnaPicker()V
    cancelActivePlaybackPreparation()V
    retryLyrics()V
    completeLyricsDragSeek()V
    seekToPosition(J)V
    setLoopPlaybackEnabled(Z)V
    setVolumeFromUser(D)V

没有任何 collapse / close / dismissPlayer / navigateUp 之类的方法。

结论：**"收起全屏播放页"是纯 UI / 导航动作，不是业务状态变更。**
onCollapseClick 和拖动松手两条路径最终都落到"把这一层收掉"，
不经过 ViewModel，不会引起播放状态、队列、上报之类的副作用。
（这也解释了为什么这个动作做起来是纯动画、不需要等任何数据。）

7. 沉浸式 chrome（控件自动隐藏）
=====================================================================

rememberImmersiveChromeState 构造出来的东西是： [DEX]

    · 一个 Boolean 状态      （chrome 是否可见）
    · 两个 MutableState
    · 一个 CoroutineScope
    · 一个 Long              （自动隐藏延时，毫秒）

里面有一个本地函数 recordUserInteraction
（方法引用字符串里能看到 rememberImmersiveChromeState$recordUserInteraction），
即"每次用户操作就把隐藏计时器重置一次"。

电视端是另一套：TvNowPlayingImmersiveHolder + ImmersiveChromeState，
有 exitImmersiveMode 这种显式退出方法。 [DEX]

推断：顶部那条把手在 chrome 隐藏时大概率一起淡出，
因为播放页整体是"全屏沉浸、控件自己会消失"的形态。 [推断]


=====================================================================
8. 歌词区的拖动是另一件事，别搞混
=====================================================================

播放页里还有第二种拖动，作用完全不同：**在歌词区上下拖动 = 拖进度。** [DEX]

  · NowPlayingLyricsCallbacks.onLyricsDragStateChange  → 拖动中（上报状态）
  · NowPlayingLyricsCallbacks.onLyricsDragFinished     → 松手
  · PlayerViewModel.completeLyricsDragSeek()           → 松手时才真正 seek

配合的标签：player.lyricsScrollContainer / player.lyricsActiveLine /
player.lyricsSyncedLine / player.lyricsPanel。

也就是说：
  · 页面级垂直拖动（第 4 节）→ 收起页面
  · 歌词区拖动（本节）      → 定位播放进度，且松手才提交
两者靠"手势落在谁身上"区分：歌词区自己吃掉手势。

9. 背景
=====================================================================

播放页背景是自绘着色器，不是静态图也不是简单渐变。 [DEX]

dex 字符串池里能读到：
  · "ColorfulX shader program 创建失败"（ColorfulX 那套流动渐变着色器的移植）
  · 两段被编进二进制的中文源码注释：
      "按短边归一化：竖屏时 s=width（与原实现一致），横屏时 s=height，
       两向都保持圆形光斑并铺满。"
      "power 恒为 4：pow(dist, 4) ≡ (dist²)²，用 dot 代替 length+pow。"
    即光斑是按短边归一化的圆形径向衰减，指数固定为 4，
    并用点积替掉 length+pow 做优化。
  · 渐变色由 NowPlayingGradientColors(top, bottom) 提供，
    再由一层 player.fullscreenBackgroundLayer 铺在内容下面。
  · 主题背景另有一套资源：assets/theme_backgrounds/system_preset.png。

两段注释基本把着色器核心算法说清楚了：
    dist = 到光斑中心的距离（按短边归一化）
    glow = 以 dist^4 为衰减核，叠成 top / bottom 两色之间的过渡

11. 没能确定的部分
=====================================================================

  · 那条横条本体的尺寸与颜色值：只确认外框热区 38dp×38dp、
    颜色是主题派生色（一份带 alpha 0.7f），
    横条自身的长 / 宽 / 圆角 / 具体灰度没读到。

  · 拖动过程中除了"整页位移"以外还有没有别的视觉响应
    （缩放、圆角变化、背景视差、透明度），没有确定。
    只读到位移量被一个 Animatable 持有并被动画驱动。

  · 速度阈值 1800 / -1600 的单位到底是 px/s 还是 dp/s，
    以及 0.3 / 0.7 各自对应"收起"还是"展开"分支，
    受 R8 合并 lambda 后的控制流影响没能 100% 对齐。

  · 哪些布局模式走 snapTo（不做过渡）、哪些走 spring，
    只确认存在这条分支（枚举常量 Lv45.b），没有还原出完整判定。

  · 点把手收起和拖动收起是否共用同一段收尾逻辑，未确认。

  · 横屏的 landscapeDismissButton 是按钮还是也带拖动，未确认。

  · iOS / 桌面端（截图来自 iOS）与 Android 是否逐像素一致，未验证。

上面剩下的这些，唯一可靠的办法是在真机上录屏逐帧量
（跟手比例、回弹时长、甩动判定都能从帧里量出来）。
纯静态分析到这一层已经到顶了。
