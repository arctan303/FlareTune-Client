Apple Music · Android 7.0.0 (1614) · com.apple.android.music
全屏播放页 · 歌词间奏指示器（三个圆点） · 实现事实

=====================================================================
0. 这份材料是什么 / 怎么来的
=====================================================================

对象：Apple Music Android 7.0.0 (1614)，包名 com.apple.android.music。
      split APK：base（79.5 MB，classes.dex ~ classes4.dex）+ config.arm64_v8a。
来源：apkpure 直链下载的 split 包，本地解包后直接读资源表与字节码。

取证方式：
  · 资源（布局 / drawable / dimens / color）→ androguard 解 ARSC + AXML，
    把所有 @0x7f…… 资源 ID 反查成名字，dimen 附上真实数值。
  · 行为 → 直接读 dex 里的 dalvik 指令。这个 App 的类名被 R8 压成了
    Lcom/apple/android/music/player/x; 这种，但 **方法名、字段名、
    字符串常量、PathInterpolator 的四个浮点参数、ValueAnimator 的
    duration/repeatMode、fill-array-data 的浮点表** 全部保留，
    所以下面每一条都能落到具体指令或具体数值上。

标注约定：
  [XML]  = 反编译出来的布局/drawable 资源原文
  [DEX]  = 字节码直读
  [推断] = 由字节码结构推出、没有直接常量佐证

最后一节列没能确定的部分，不要把那节当已知。

本文只讲**间奏指示器**（歌词流里那三个圆点）。
歌词逐字卡拉 OK、整页进出场、背景流动层不在本文范围。


=====================================================================
1. 先说结论
=====================================================================

它不是"三个点循环闪一下"的装饰动画，而是**一条三格进度条**：

  两段歌词之间的空白如果 ≥ 7 秒，歌词列表里会插一行三个圆点。
  这一行的总时长 E = 空白时长 − 800ms。
  三颗圆点把 E 均分成三段，从左到右依次由"18% 白"渐亮到"94% 白"，
  填满的顺序就是间奏推进的顺序 —— 用户看到的是"间奏还剩多少"。

  在此之上叠了一层**呼吸**：整行（不是单颗）以 1.0 → 1.2 → 1.0 缩放，
  一拍约 4 秒，重复次数按剩余时间取整，最后一拍正好踩在间奏结束。

  间奏结束、这一行要从列表里退场时，还有一段 1.75 秒的收尾：
  补完最后一格 → 放大到 1.2 → 缩到 0.5 并淡出。

一句话概括手感：**底色是进度，节奏是呼吸，退场是一次"吸满再吐掉"**。
两颗圆点之间没有任何独立动画，所有动效都挂在"行"和"每格的色值"两个层级上。

2. 它长什么样
=====================================================================

布局：res/layout/lyrics_line_instrumental.xml   [XML]

  ConstraintLayout  id=lyrics_instrumental_root
                    tag="layout/lyrics_line_instrumental_0"
    layout_width  = match_parent
    layout_height = wrap_content
    layout_marginStart / marginEnd = lyrics_line_margin_horiz   = 20dp
    paddingStart / paddingEnd      = lyrics_text_padding_horiz  = 12dp
    paddingTop                     = lyrics_text_padding_top    =  2dp
    paddingBottom                  = lyrics_text_padding_bottom = 10dp

    ImageView id=dot1   10dp × 10dp   marginLeft 6dp  marginRight 6dp
    ImageView id=dot2   10dp × 10dp                  marginRight 6dp
    ImageView id=dot3   10dp × 10dp                  marginRight 6dp

  · 三颗尺寸都取 lyrics_instrumental_dot_size = 10dp
  · 间距都取 lyrics_instrumental_dot_margin_horiz = 6dp
  · 水平链 chainStyle = packed（不是 spread），horizontal_bias = 0
    → 三颗整体贴着行的左边缘，不是居中
  · 行高 = 2 + 10 + 10 = 22dp
  · 三颗占位宽 = 6 + 10 + 6 + 10 + 6 + 10 + 6 = 54dp
  · 视觉起点 = 屏左 20（margin）+ 12（padding）+ 6（dot1 marginLeft）= 38dp

圆点本体：res/drawable/lyrics_instrumental_dot.xml   [XML]

    <shape android:shape="oval">        ← 正圆，不是圆角矩形
      <solid android:color="#000000"/>  ← 纯黑，靠 tint 上色
      <size width=10dp height=10dp/>
    </shape>

  在布局里：
    android:scaleType = center
    android:tint      = @color/white_alpha_85   = #D9FFFFFF（85% 白）
    android:tintMode  = SRC_IN

  也就是说：**默认态是 85% 白的实心圆**，只有 10dp 大，没有描边、没有阴影、
  没有渐变、没有模糊。

运行时颜色   [DEX]

  适配器构造时从 Resources 取三个颜色，存成字段：

    H = @color/player_vibrant_primary    → 兜底 white_alpha_94 = #F0FFFFFF
    I = @color/player_vibrant_tertiary   → 兜底 white_alpha_18 = #2EFFFFFF
    （另有 @color/player_vibrant_35 → white_alpha_35 = #59FFFFFF，
      用在字级卡拉 OK 的色组里，不参与圆点）

  player_vibrant_* 全是"动态色"引用 —— 真机上由当前封面取色覆盖，
  所以真机看到的不是白，而是封面主色系的三个明度档。
  静态分析只能确定兜底值：**primary 94% 白 / tertiary 18% 白**，
  以及"未填 = 暗档、已填 = 亮档"这个方向关系。


=====================================================================
3. 什么时候出现、持续多久
=====================================================================

适配器在提交歌词行时算一个整数 E（毫秒），逻辑是：   [DEX]

    if (这一区间里没有任何歌词行 && 区间时长 >= 7000ms)
        E = 区间时长 - 800;

  · 7000 是硬门槛：**空白短于 7 秒就不播**（那一行仍然在列表里，
    但动画时长字段 E 不更新，渲染函数会因为"剩余时间 <= 0"直接 return）。
  · E 不是空白时长本身，而是空白 **减 800ms**。
    这 800ms 是给下一句歌词留的提前量（下一句的字级动画需要预热）。

  渲染入口：Y(binding, isRtl, isActiveLine)   [DEX]
    · onBindViewHolder 调用一次
    · 视图 attach 时再调用一次
  进来第一件事：把三颗的 tint 全部重置成 I（18% 白，未填态），
  然后按当前播放进度决定每一颗处于"未开始 / 正在填 / 已完成"哪个状态。
  所以它天然支持"拖进度条跳到间奏中间"—— 不会从头再演一遍。


=====================================================================
4. 填充：三格进度条怎么分时间
=====================================================================

设 E 为上一步算出来的间奏时长（ms），先算一格的长度：   [DEX]

    seg = round( (E + 750) / 3 )

三颗的窗口（start, duration）：

    dot1:  start = 0,        duration = seg
    dot2:  start = seg,      duration = seg
    dot3:  start = 2 * seg,  duration = E - 2 * seg

  · 三段的 duration 加起来正好等于 E。
  · 前两颗各占 (E+750)/3，第三颗吃掉余数，所以**第三颗比前两颗短**。
  · 第三颗的"填充比例上限" = (E - 2seg) / seg，通常 < 1.0
    —— 它在 E 到点时只填到 88% 左右，剩下那一截交给第 5 节说的尾巴。

每一颗内部：   [DEX]

    elapsed   = 主时钟 ValueAnimator 的 fraction × duration
    remaining = (start + duration) - elapsed

    if (remaining <= 0)         → 直接 setImageTintList(I 的对面：primary)
    else if (elapsed <= start)  → 保持 I，等 start - elapsed 毫秒后从 0 开始填
    else                        → 从 (elapsed - start) / duration 起，
                                  线性插值到 (duration / seg)，用 ArgbEvaluator 走 I → H

  颜色插值器是 ArgbEvaluator（Android 内置，直接按 ARGB 分量线性插），
  没有额外曲线 —— 也就是说**颜色的明暗变化是匀速的**。

  时间曲线的柔化放在 ValueAnimator 的 Interpolator 上：

    PathInterpolator(0f, 0.5f, 1f, 0.6f)      // cubic-bezier(0, 0.5, 1, 0.6)

  这条曲线起手就快、后段收住 —— 每一格都是"啪一下亮起来，然后慢慢到头"。

最后一格的尾巴   [DEX]

  第三颗额外挂一条独立动画：

    ofFloat(当前比例, 1.0f)
    duration      = 750ms
    interpolator  = LinearInterpolator      ← 注意是线性，不是缓动
    update        = 同一套 ArgbEvaluator(I → H)

  它和 E 的关系是设计好的：
    E          = 空白 - 800
    尾巴 750ms
    → 填满时刻 = E + 750 = 空白 - 50ms

  也就是说**最后一颗圆点在下一句歌词出现的 50ms 前刚好填满**。
  800 减 750 剩下的这 50ms，就是留给"填满"这个状态被看见的时间。

举个具体数（空白 20s）：

    E    = 20000 - 800 = 19200
    seg  = round(19950 / 3) = 6650
    dot1  0     → 6650
    dot2  6650  → 13300
    dot3  13300 → 19200，填到 5900/6650 = 88.7%
    尾巴  19200 → 19950 补到 100%

5. 呼吸：整行在做 1.0 → 1.2 → 1.0
=====================================================================

挂的不是单颗圆点，是整行的 ConstraintLayout（lyrics_instrumental_root）：  [DEX]

    ObjectAnimator.ofPropertyValuesHolder(root,
        SCALE_X: [当前值, 1.2f, 1.0f],
        SCALE_Y: [当前值, 1.2f, 1.0f])

    repeatMode  = RESTART
    基准 duration = 4000ms

  第一次循环从"当前 scale"起跳，之后每次 onAnimationRepeat 里把关键帧
  重设成 [1.0, 1.2, 1.0]，所以稳态是 1.0 → 1.2 → 1.0。

  1.2 是 0x3F99999A；10dp 的圆点放大到 12dp，三颗连同 6dp 间距一起放大，
  但整行宽度只有 54dp，放大 20% 也就多出 11dp —— 视觉上是"轻轻鼓一下"。

时长按剩余时间均分：   [DEX]

    count    = 剩余时间 / 4000        （整数除法）
    duration = 剩余时间 / count
    repeatCount = count - 1

  → 每拍 4 秒左右（剩余时间不能整除时会被拉长一点点），
    拍数取整后正好把剩余时间铺满，最后一拍结束 = 间奏结束。
    例：E = 19200 → count = 4 → 每拍 4800ms，重复 3 次（共 4 拍）。

呼吸的曲线不是 PathInterpolator，是一张 **97 点查找表**：   [DEX]

  LX9/a; 里有一张 97 个 float 的静态数组（步长 1/96），
  getInterpolation 做"找到区间 → 线性内插"，两端夹在 [0,1]。

  这张表有两个很明显的特征（逐点算出来的）：
    1) 前后两半完全同形：y(t + 0.5) = y(t) + 0.5
    2) 端点和中点几乎是平的，中间有两处最快

         t=0.000  y=0.000   斜率  —
         t=0.125  y=0.058   斜率  0.96
         t=0.208  y=0.194   斜率  2.11   ← 最快
         t=0.250  y=0.279   斜率  2.11
         t=0.375  y=0.458   斜率  0.77
         t=0.500  y=0.500   斜率  0.05   ← 几乎停住
         t=0.625  y=0.558   斜率  0.96
         t=0.708  y=0.694   斜率  2.11   ← 最快
         t=0.875  y=0.958   斜率  0.77
         t=1.000  y=1.000   斜率  0.05

  换到 scale 上（关键帧 1.0 / 1.2 / 1.0，峰值在 y = 0.5）：
    · 起步极慢（斜率 0.05 ≈ 前 10% 时间里只动 1%）
    · 中段快速鼓起来
    · 接近 1.2 时缓住，在峰值附近停一小会儿
    · 回落同样先缓后快再缓
  这就是"呼吸"而不是"脉冲"的原因 —— 没有尖锐的折返点。

  同一张表在别处也用了（Lcom/apple/android/music/player/S0;->U），
  不是给圆点专门画的。

pivot（缩放的支点）   [DEX]

    pivotX = 行首内侧（leftMargin + paddingLeft）或行尾内侧
             （width - rightMargin - paddingRight），二选一
    pivotY = paddingTop + topMargin + 内容高 / 2      ← 内容区垂直中心

  · 视图还没布局完（!isLaidOut || isLayoutRequested）时不硬算，
    挂一个 OnLayoutChangeListener，等布局回调里再补 pivot。
  · 行首还是行尾，由 (是否 RTL) × (是否当前行) 两个布尔量组合决定，
    四个分支的具体语义没能完全对齐，见第 8 节。


=====================================================================
6. 退场：补完 → 鼓到 1.2 → 缩到 0.5 淡出
=====================================================================

这一行离开列表时，走一段 1.75 秒的收尾（N 方法，挂在 ItemAnimator 回调上）：   [DEX]

    ① 最后一格补色      750ms   LinearInterpolator
       从当前比例补到 1.0，仍然是 ArgbEvaluator(I → H)
    ② 放大到 1.2        750ms   PathInterpolator(0.5, 0.1, 0.5, 1.0)
       起点是"当前 scale"，通常就是 1.0 或呼吸中途的某个值
    ③ 缩到 0.5 + 淡出   250ms   PathInterpolator(0.5, 0, 1.0, 0.2)
       SCALE_X / SCALE_Y → 0.5，ALPHA → 0，两条 with 并行

    三段是串行 after 关系：① → ② → ③

  两条曲线是一对：
    ② (0.5, 0.1, 0.5, 1.0)  收尾缓 —— 放大后"停得住"
    ③ (0.5, 0,   1.0, 0.2)  起手缓、末尾陡 —— 缩下去"收得干净"

  结束回调里把 scale / alpha 复位成 1，三颗 tint 复位成 I（18% 白），
  也就是把这一行还原成可复用的初始态。

  另有一个 M 方法：取消当前动画、清空动画字段、并把列表滚一下（见下节）。
  它不做视觉，只是"打断 + 复位"。

7. 和播放状态 / 滚动的关系
=====================================================================

暂停与恢复   [DEX]

    J() / K()  →  AnimatorSet.pause()  +  ValueAnimator.pause()
    L()        →  AnimatorSet.resume() +  ValueAnimator.resume()

  两处都同时管"填充组"和"主时钟"，所以暂停时圆点会**停在当前色值**上，
  不会继续走也不会回弹。调用方是 PlayerLyricsViewFragment;->X1(I)。

给 native 歌词引擎的行偏移提示   [DEX]

  填充组开始 / 取消时各调一次：

    onAnimationStart   →  d2(-1300)
    onAnimationCancel  →  d2(-500)
    M()（打断复位）    →  d2(-500)

  d2 进去是 SongInfoTimeProcessorNative.suggestLineOffset(int)，
  单位是**毫秒**，不是像素 —— 是给 C++ 侧的歌词时间处理器的行偏移建议值，
  让它提前 1.3 秒 / 0.5 秒把"当前行"往目标位置挪。

8. RTL 与方向
=====================================================================

  Q0.a(String) 的判断是：取第一个字母，字符码在 1424..1791 之间就返回 true，
  这是阿拉伯字母 + 希伯来字母的 Unicode 区间 —— 也就是 **isRtl**。   [DEX]

  isRtl 为真时，渲染入口第一件事是 Collections.reverse(三颗的列表)，
  于是填充顺序变成从右往左。呼吸的 pivot 也相应换到另一侧。

  pivot 的四个分支（是否 RTL × 是否当前行）逐条读出来是：

    RTL=1 当前行=1  → 支点在左
    RTL=1 当前行=0  → 支点在右
    RTL=0 当前行=1  → 支点在右
    RTL=0 当前行=0  → 支点在左

  这个组合方式（同或关系）跟"RTL 就翻到另一侧"的直觉不完全一致，
  没能从字节码里读出它的业务理由，列进第 10 节。

10. 没能确定的部分
=====================================================================

1. 真机上三颗圆点的实际 RGB。player_vibrant_* 是动态色，由封面取色覆盖，
   静态分析只能拿到兜底色（94% 白 / 18% 白），拿不到运行时值。

2. 退场动画 N() 到底挂在 ItemAnimator 的哪个回调上。
   能确认的是形态（补色 → 鼓到 1.2 → 缩到 0.5 淡出），
   但 $u 里 p/q/r/s 四个转发方法对应 appearance / disappearance 的哪两个，
   没有从基类 Llc/y 里读出来。

3. pivot 的"同或"组合（RTL == 当前行 时支点在左）的业务理由。

4. 呼吸第一拍的关键帧是 [当前 scale, 1.2, 1.0]，绑定那一刻 scale 一定是 1
   这个前提由谁保证（复位在退场结束时做，但中间态没追）。

5. E 只在"区间无歌词且 >= 7000ms"时被赋值，空白变短时 E 是否被清空
   没有读到清空指令 —— 有可能是沿用上一段的陈旧值（渲染入口会因此直接 return，
   所以表现上仍是"不播"，但字段状态不干净）。

6. 三颗圆点在深色/浅色两套主题下是否有不同的 tint。
   布局里写死的是 white_alpha_85，没有读到 night 限定目录下的同名资源。

7. iOS / 桌面端的同一元素是否逐值一致。
